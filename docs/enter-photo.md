# Enter Photo：从一张照片进入可交互生成场景

更新：2026-10-05。用户最新明确要求覆盖此前“先做固定图生视频”的冲刺优先级。目标是选中/输入一张照片后，看到场景，使用 WASD 移动、鼠标或方向键转动视角，并根据刚看到的画面继续探索。不是输入整条轨迹后等待一个 MP4，也不是反复拿末帧重新启动独立图生视频。

**后续确认：不要求实时，最终用用户提供的雪山与建筑两张照片，各至少10秒成片，生成可以等待。** 因而交互按“选择动作→等待→查看→再选择”的形式推进，不再将低延迟作为首版硬门槛。两张照片的预设轨迹成片是演示素材阶段，不代替有状态交互验收。见 [双图Demo记录](benchmarks/user-world-demo-20261005.md)。

## 当前事实与边界

- 原有 Wan2.2 固定视频流程已实测可用，但**不满足交互探索**。一次真实网页任务生成 49 帧、24fps、约 2.04 秒视频，worker 耗时 83.842 秒。这个数字属于 Wan，不是 LingBot 的延迟或帧率。
- 当前优先接入官方 LingBot World v2 的 1.3B causal-fast 预训练模型。不训练，不租卡；在用户现有 3090 服务器上独立部署。
- 官方代码支持首图、文字与相机位姿条件、分块因果生成和 KV 缓存。但原生 `generate()` 每次初始化缓存，并在整段完成后解码。它不是现成的交互服务。必须将同一会话的生成状态保留到下一次操作，才能交付用户要求。
- 固定版本的15个模型文件已全部下载并校验，独立环境检查通过；首条21帧离线轨迹已真实生成并经ffprobe复核。输出832×464、1.3125秒，整段生成66.765秒，另模型加载152.552秒。证据见 [单卡记录](benchmarks/world-runtime-20261005.md)。**尚未完成交互，当前基线不实时**，不能从模型规模推断单张3090可实时。
- 已新增纯 CPU 相机动作/位姿契约，独立实现标准 SE(3) 变换；仅证明输入约束与几何数学，不证明生成画面服从操作。代码没有模型、HTTP服务或网页探索入口。
- 生成的遮挡后方和图外内容是模型推测，不是对真实场景的测量；暂不承诺准确几何、碰撞、无限记忆或回到原处完全一致。

## 数据流与真正需要实现的部分

1. 本地网页选择图片，显示实际输入裁剪，并单次确认发送到用户自己的服务器。首版仍使用公开/授权图，不默认上传整个相册。
2. 创建一个世界会话，绑定图片哈希、模型revision、种子、分辨率、相机标定和会话所有者。
3. 网页发送递增编号的移动/观察事件。服务端限幅、排序、幂等去重；拒绝过期、跨会话或超范围操作，不能通过排队无限积压“早已松开的按键”。
4. 同一个会话保留 DiT KV/cross-attention cache、随机数状态、帧偏移和相机状态；分块生成与增量 VAE 解码要保留时序状态。
5. 返回新帧和已执行事件编号，网页播放后继续接受操作。明确显示加载、生成、传输、等待和真实延迟，不用去噪步数冒充全程完成百分比。
6. Reset/Close清理该会话自己的缓存；单卡首版只允许一个活跃生成会话。只经私有回环服务与SSH隧道访问，不开放公网端口。

第2–6步是待实现的交互服务，不是当前已交付能力。离线动作轨迹只作为模型可控性烟测，不替代最终验收。

## 相机契约：为什么不把 WASD 直接塞进提示词

原生快速路径读取 `poses.npy`，形状 `(N,4,4)`，表示 OpenCV camera-to-world 绝对位姿：X向右、Y向下、Z向前；另读 `[fx,fy,cx,cy]` 内参，固定以832×480为标定参考。我们的动作层把移动/转向转为位姿，再由上游构造相机条件。当前不恢复照片真实焦距，后续若用假定视场角，必须标为假定而非测量。

上游会抽样、转相邻相对位姿并归一化平移，所以不能把输入1单位叫作在画面里准确前进1米。我们显式选择latent chunk=3（Python方法默认3，但官方CLI默认4，不能混用），不是所有4k+1帧都能完整保留：在chunk=3下，49帧会被静默裁至45帧。动作契约显式拒绝这种情况；9、21、33、81等对齐长度才允许以该chunk设置导出。连续交互还需单独处理chunk边界，不能无限重复首图初始化。

## 三天执行优先级与验收门槛

| 顺序 | 工作 | 通过条件 |
| --- | --- | --- |
| D1 可运行性 | 隔离依赖、权重完整性、3090算子、小尺寸/短轨迹模型烟测 | 真输出、输入/配置/日志留档；无OOM；记录真实首帧/总耗时和显存 |
| D2 可交互性 | 有状态会话、动作条件、增量帧回传、最小网页控制 | 用户看到第一段后再改变方向，第二段仍延续同一会话；不是预录或独立拼接 |
| D3 可演示性 | 延迟优化、长一点的会话、重置/断连/取消、固定场景验收 | 至少连续20次操作，记录延迟分布、吞吐、失败、漂移；公开真实视频与局限 |

这是剩余72小时窗口内的目标优先级，不额外承诺顺延三天。若单卡达不到流畅体验，先报告实测，再决定降分辨率/上下文/帧块，或明确标为等待式交互；**等待式交互也不能包装为实时漫游**。不擅自占用其他任务的GPU。

## 量化与面试表述

- 测端到端首帧延迟、输入事件到对应新帧延迟p50/p95（样本不足不写百分位）、生成帧/秒、播放帧/秒、GPU allocated/reserved峰值和会话失败率，区分冷启动/热启动。
- 固定公开输入、种子、动作脚本和运行版本；做左右/前后反向操作、停留、转回原方向；保留全部失败，人工检查方向响应和漂移。几何契约单测不充当感知质量分数。
- 优化对照一次只改一项，保持输入和动作相同，保留原始视频及抽帧。没有修复后结果就写“未测”，不画虚构提升曲线。
- 面试常见问题：为什么不是普通I2V？KV缓存保留了什么/丢了什么？为何有了camera pose还会漂移？真实几何与生成世界有何区别？单卡瓶颈在DiT还是VAE？为什么4步不等于4倍加速？如何防止过时操作排队？如何证明个性化是偏好记忆而不是偷偷训练？

一句话总结：保留已有美学与选片能力，把视频方向的验收从“输出MP4”改为“同一状态下看见后再控制”，先用官方预训练世界模型验证单3090的真实边界，再做会话和延迟优化，不用固定视频冒充自由探索。
