# 三天 Demo：不训练的个人偏好案例重排

## 这是什么，不是什么

首版是 **冻结 OpenCLIP 向量上的偏好案例检索与重排**：保存用户在具体任务中选了哪张、没选哪张，后续遇到相近任务时，给相似候选有限的加减分。

它不更新神经网络参数、不拟合用户向量、不训练奖励模型；不是 DPO、SFT 或 VLM-RAG。提供能力的是预训练 OpenCLIP 的表征；检索、门限和加权公式是明确写出的 Demo 策略。它可能学习不到独立于主体内容的真正审美，不能把“偏好记忆开始影响结果”写成“已验证理解用户审美”。

## 用户能看到的变化

1. 默认仍是 `record-only`，记录反馈但不改变排序。
2. 在一次选片请求中显式启用偏好记忆，才调用这个模块；不能静默打开。
3. 新增一次有明确胜负的照片比较，再用相近任务选片，可以在结果中查看分数修正及对应反馈事件 ID。
4. 没有适用记忆、只有平局/跳过、模型不同或历史图片变了，修正就是零，保留原结果。
5. 人数、张数等硬约束仍由后面的约束优化器决定。记忆只改软分数，不直接强行替换最终照片。

接入方应把记忆开关与历史 `adaptive` 训练模式分开。三天 Demo 仅在 `record-only` 下允许显式案例重排，避免在用户以为“不训练”的时候混入旧的训练型适配器。

## 具体算法

查询、候选照片、历史选中/拒绝照片都使用同一固定 OpenCLIP 提供方的 512 维单位向量。只读取同一用户、同一提供方的最多 64 条最近 `preferred` 反馈；平局、跳过和“两张都不好”不被强行转成正负例。

对于历史事件 e：

```text
q      = 当前查询的单位向量
q_e    = 记录事件时的查询单位向量
p_e    = 历史选中照片单位向量
r_e    = 历史拒绝照片单位向量
x      = 当前候选照片单位向量

s_e = cosine(q, q_e)
若 s_e <= 0.2，则该事件不参与。
w_e = ((s_e - 0.2) / 0.8)^2

contrast(x, e) = (cosine(x, p_e) - cosine(x, r_e)) / 2
delta(x) = 0.15 × sum(w_e × contrast(x, e)) / max(1, sum(w_e))
```

最多使用最相关且通过完整性检查的 8 条案例。使用 `max(1, sum(w))`，是为了让一条勉强相关的案例保持弱影响，不能被归一化成满强度。单位向量的对比项在 −1 到 1 之间，最终修正也会明确截断在 **−0.15 到 +0.15**。它是软评分尺度上的修正，不是概率或百分比。

相同选中/拒绝对、相同规范化任务和来源的重复事件只使用最近的一条，避免连续点击重复反馈放大影响。排序和同分处理固定，不引入随机性。

## 为什么不能直接复用之前所有反馈？

原来的不可变 `preference_events` 虽有照片 ID 和投影特征，却没有完整源图片/向量文件哈希。照片重新导入后，即使 ID 相同，也不能证明当前图片就是当时被比较的内容。

因此，新反馈才会额外记录 `context.memory_evidence`：

- 固定证据版本、提供方身份与维度；
- 事件发生时的查询向量；
- 选中和拒绝照片的 ID、原图 SHA-256、向量文件 SHA-256。

读取历史案例时会再次核验源文件实际字节、向量文件字节、数据库归属和提供方。源图内容改变但大小/时间戳被恢复，也会被排除。重新索引新图片不会把旧偏好自动迁移到新图片。

缺少证据的老事件只显示 `missing_immutable_evidence` 警告并跳过，不回填一份“现在的哈希”冒充历史证据。既有 8 对代理标注没有被本模块导入。

## 标注来源不能混淆

- 现有应用比较界面的事件来源 `selection-pairwise-feedback` / `pdrr-suggestion-feedback`，输出标记为 `interactive_feedback`，表示来自交互反馈流程，不是独立审美真值认证。
- `assistant_proxy` 默认排除。只有同时显式开启 `allow_proxy`、带用户授权标记、`human_observed=false` 才能参加；输出引用仍标记为代理，不伪装成人工观察。
- 后续独立评测不能以开发时使用的这些代理案例本身作为留出测试集。

## 后端接口

```python
from ai.preferences.memory import MemoryReranker

result = MemoryReranker(
    database, provider,
    enabled=True,       # 接入方必须对应用户显式选择
    allow_proxy=False,
    max_events=64,
    top_k=8,
    max_delta=0.15,
).rerank(user_id, query_vector, candidate_vectors)
```

`candidate_vectors` 是 `{photo_id: np.ndarray}`；接入方负责验证当前候选，且必须传入实际排序所用的查询向量。模块不会重新调用大模型，也不会写数据库。

返回值：

- `deltas`：每张候选的软评分修正；
- `citations`：每张候选的事件 ID、来源、查询相似度与实际贡献；
- `event_ids`：本次参与计算的历史事件；
- `enabled` / `applied`：开关状态与是否产生非零影响；
- `reviewed_event_count` / `skipped_counts` / `warnings`：预算、无证据、过期、无关等原因；
- `as_dict()`：可直接放入响应和审计记录的 JSON 结构。

新反馈证据由 `build_memory_evidence()` 构建，已接入 `PreferenceService.record_pairwise()` 的新上下文事件路径。它不改变默认 `record-only` 的训练开关，也不修改已有不可变事件。

## 验证与优化顺序

单元测试验证：默认不启用、无历史零变化、确定性与幅度上限、同用户/同模型隔离、平局与代理排除、事件引用、原图/向量漂移、老事件不回填、默认模式不训练。单元测试里的向量是受控测试数据，不代表用户收益。

后续真实对比采用固定候选集和硬约束，分别比较无记忆、相关记忆、随机记忆。记录人工独立偏好一致率、用户替换次数、满足约束率与增量耗时；按照片来源/事件拆分，不能用看过的图验证泛化。再考虑风格属性去混淆、记忆质量过滤和基于证据的大模型解释。没有独立结果前，不报告“审美提升 X%”。

一句话总结：先用已有预训练表征和可审计的交互案例，低成本展示“反馈如何影响下一次选片”，同时保留关闭开关、原始基线、硬约束和来源证据；后续再验证是否真的对新照片、真实用户有帮助。
